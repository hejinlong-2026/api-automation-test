> 面试官不会问“你用了什么工具”，他问的是“你怎么发现问题”。
> 下面每一条都按 **现象 → 分析 → 结论** 组织，直接背结构，别背字。

## 1. 30 秒介绍（开场必用）

> 我这个项目是在本地搭了一套电商交易接口，用 pytest 做了 43 条自动化用例，
> 覆盖登录、商品、购物车、下单、支付到订单查询的完整链路。
> 跑完发现 3 个缺陷，其中一个重复支付没有幂等控制，是会重复扣款的资损问题。
> 我最后给了一份测试总结报告，结论是不建议发布。

**要点**：数字化（43 条 / 3 个缺陷）、完整链路、有结论有判断。不要背技术栈清单。

## 2. 高频追问与答法

### Q1：为什么不用 Postman 而是 pytest？

> Postman 适合调通和手工回归，但它不是测试资产。
> 接口一改，几十个用例要手工点一遍；pytest 里 URL 集中在业务层一个文件，
> 改一处全量生效，而且能进 CI 每次提交自动跑。
> 我用 Postman 做接口探查，用 pytest 沉淀可回归的用例，两者不冲突。

### Q2：你的断言怎么写的？

> 分三层。第一层 HTTP 状态码；第二层业务码 `body.code`，因为企业接口 HTTP 常是 200，真实结果在 code 里；
> 第三层数据结构，用 jsonschema 校验字段类型和必填，比逐个 assert 更容易发现字段缺失和类型漂移。
> 另外我封装了断言方法，失败信息直接是“期望 404 实际 200，body=xxx”，能原样贴进缺陷单。

### Q3：用例之间会不会互相影响？

> 会，这是我自己踩的坑。一开始我把“未登录访问”写成复用 session 级 client，
> 前面用例给它设过 token，这个用例就一直假失败。
> 后来改成这类场景新建独立 client，业务数据用 function 级夹具每次新建订单，保证隔离。

*（这是加分项：主动说踩过的坑比说“我设计得很好”可信 10 倍。）*

### Q4：怎么保证用例有效而不是一堆通过？

> 我的做法是失败必须可解释。3 条失败我逐条核对是被测系统的问题还是我脚本的问题：
> 比如“加购数量等于库存返回 400”，我去查了实现，发现是 `qty > stock` 写成了 `qty >= stock`，
> 这是边界值实现错误，不是我的用例错。如果一条用例怎么改都通过，那它大概率没在验证任何东西。

### Q5：你说发现 3 个缺陷，挑一个讲深一点

**（推荐讲 D-003 重复支付，最能体现质量意识）**

> 现象：同一订单连续调两次支付接口，两次都返回 200 成功。
> 第一次返回 `status=PAID`，第二次返回 `{"status":"PAID","repeated":true}`。
>
> 分析：接口没有做状态校验，也没有幂等键。表面上看“没有重复扣款”，
> 但因为我这个 mock 服务没有接真实支付网关，一旦接上，第二次请求会再触发一次扣款，
> 结果是用户付了两次钱、系统只有一个订单 —— 这是资损。
> 而且用户网络慢时连点两次按钮，前端两次都收到成功，没法提示“已支付”。
>
> 修复建议我给了三条：支付前校验状态返回 409、请求带幂等键由网关去重、加分布式锁防并发双写。
> 严重度我定的是 S1、优先级 P0，属于发布阻断项。

### Q6：数据驱动怎么做的？好处？

> 购物车模块的用例数据抽到了 yaml，一条 yaml 一个场景。
> 好处是产品规则变了（比如分页上限 100 改 50），只改数据文件，不动代码、不用重新 review 逻辑。
> 代价是断言逻辑复杂时不适合硬套数据驱动，我这边只把“输入 + 预期状态码 + 提示语”放进去，断言逻辑仍留在代码里。

### Q7：性能测试你做了吗？

> 只做了轻量基线，不算真正的性能测试。我对商品列表接口设了 500ms 的 SLA，超了就失败。
> 真正的并发、超卖场景我还没覆盖，这是这个项目明确的缺口 ——
> 下一步想用 locust 做 50 并发抢 5 件库存，验证超卖。

*（不会就说不会，但要说出你打算怎么做。面试官讨厌的是编。）*

### Q8：这个项目最大的不足是什么？

> 三块。一是没有接数据库断言，库存和订单状态落库一致性我没验证；
> 二是并发没测，超卖是电商最典型的缺陷，我现在测不到；
> 三是被测服务是我自己写的，天然比真实系统“干净”，真实的坑（历史数据、脏数据、依赖服务超时）我还没遇到。
> 所以我把它定位成“框架能力证明”，不是“生产级测试经验”。

## 3. 简历上这句话建议怎么改

**现在**：
> 使用 pytest+requests 编写接口自动化脚本，覆盖 GET/POST/PUT/DELETE，完成状态码、JSON 响应断言

**问题**：只说了用了什么，没说发现什么。面试官看不出你的价值。

**改成**：
> 自建电商交易链路被测服务（登录→加购→下单→支付→查询），基于 pytest+requests 设计 43 条自动化用例，
> 采用分层封装（接口层/断言层/数据驱动）与 JSON Schema 校验，自动化覆盖 100%，单轮执行 3s；
> 发现 3 个缺陷（含 1 个 S1 资损级：重复支付无幂等控制），输出缺陷报告与测试总结报告

**同理，第一条爬虫项目**：
> 设计 30+ 测试用例覆盖空白链接、404、图片损坏等异常场景，发现并跟进 18 个缺陷

这句唯一的毛病是**没有一条具体的缺陷描述**。补一句就活了：
> ……其中 1 个为图片下载中断后残留 0 字节文件（无校验），定位为缺少文件完整性校验
